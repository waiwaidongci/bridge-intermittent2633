# 市政升降桥备件补货预估

滨江市市政设施养护中心机电备件班，维护 6 座升降桥，中心库管理约 180 种备件。。养护工单和库管周盘点共同形成滚动台账。备件分析员（analyst）导入台账并跑回测，机电主管（reviewer）核对库存阈值和停用工单，采购值班员（viewer）查看结果和班报。原流程用 Excel 月均领用量估算补货。

CSV 每行对应一个备件的一周，week 用周一的 YYYY-MM-DD 日期，需求记工单确认的件数，含已发和缺货未发的需求。周记录必须连续，确认无需求时填写 0。所有备件使用同一最近结账周，补货信号取该周的可用库存、采购提前期和最低保有量。提前期为 1 至 26 个整周，数量以件计。 向机电主管和采购值班组提供逐备件的两个提前期需求预测、滚动留出误差、所用模型、补货点和库存缺口，并提示集中领用和长期零需求核查。

- 用 Excel 月均领用量补货时，零需求和漏报周容易混在一起，断货未发的需求也常被漏算。
- 集中检修一次领用十余件，平时可能数周零领用。统一月均值无法评估不同采购提前期的库存压力。
- 老型号在役和停用清单分开维护，长时间零需求的关键件与已替换备件需要逐件甄别。

## 六个业务模块

1. 升降桥备件总览
2. 周领用与库存台账
3. 需求预测与回测
4. 逐件补货信号
5. 在役与补货复核
6. 采购班报分发

## 工作剧本

1. 2026 年 11 月 24 日 08:10，备件分析员查看东闸桥和西泵桥总览，确认本次先复核 4 种备件。
2. 08:25，导入 2026-11-24_滨江升降桥备件周台账.csv，含 192 条记录，每个备件 48 个连续周，最近周为 2026 年 11 月 16 日开周。
3. 08:40，分析员设置 α=0.20、β=0.15、8 个滚动留出窗口和 8 周停用核查阈值。西泵桥导向轮轴承 HB-041 按 5 周采购提前期回测。
4. 08:45，结果显示 HB-041 的提前期需求估计为 SBA 5.32 件、TSB 4.69 件。按 TSB 估计加 3 件最低保有量，得到 8 件补货点，较 2 件现货缺 6 件。
5. 09:05，机电主管核对 HB-041 单周领用 16 件的检修工单，再查东闸桥限位开关 HB-027 的在役记录。该开关连续 15 周零需求，现有 2 件恰好到达补货点。
6. 09:30，主管核对 3 种触点备件与在途单，签发补货复核报告，保留 HB-027 停用核查意见。
7. 10:00，分析员导出逐件预测和库存信号，机电主管排定 10:15 站内分发给机电备件采购值班组。

## 算法与复核

Croston SBA 平滑正需求量和间隔并作偏差修正。TSB 逐周更新需求发生概率。用最近多个滚动起点做扩展窗口回测，按本批采购提前期评估累计需求 MAE。补货点为选中模型的提前期预测向上取整再加最低保有量。批量波动和长期零需求需要核对检修计划、缺货记录及在役状态。

备件编号对应多个桥位或名称、周次重复或不连续、最近结账周不一致、整数超界、训练加留出周数不足，都会阻断计算。按报错修正 CSV 或调整回测窗口数后重跑。 复核问题为「哪些备件触及补货点？集中检修、在途库存与在役状态核实后，哪些信号可以交采购复核？」。每次分析绑定数据版本和参数，原始数据按规范化内容的 SHA-256 去重。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `sku` | 备件编号 | str |
| `bridge` | 桥位 | str |
| `part` | 备件名称 | str |
| `week` | 结账周周一（YYYY-MM-DD） | str |
| `demand` | 周需求量（件） | int |
| `on_hand` | 期末可用库存（件） | int |
| `lead_weeks` | 采购提前期（周） | int |
| `reserve` | 最低保有量（件） | int |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18297`
- API 文档 `http://127.0.0.1:19297/docs`
- 数据库端口 `17797`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、运行分析、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、MySQL 8.0 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
